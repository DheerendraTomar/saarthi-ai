# LocalPilot VS Code Extension (+ shared chat UI) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A VS Code extension that spawns the Rust core (`localpilot-core`), shows ghost-text inline completions, and hosts a sidebar chat agent with approval-gated edits/commands — installable from a `.vsix` on the owner's machine.

**Architecture:** The extension is a thin client. `CoreClient` spawns the bundled binary and speaks newline-delimited JSON-RPC 2.0 over stdio (the contract in `core/src/protocol.rs`). `DocumentSync` mirrors open editors into the core's overlay; `InlineProvider` turns `completion/request` into `InlineCompletionItem`s with debounce + cancel; `ChatView` hosts the shared `chat-ui` bundle in a `WebviewView` and relays messages; `workspace/applyEdit` and `workspace/runCommand` (core→client requests) are applied via VS Code APIs. `chat-ui` is a separate package (Preact + Vite, single-file bundle, no external loads) so the JetBrains plugin can reuse it later.

**Tech Stack:** TypeScript 5, Node 20, npm workspaces; chat-ui: Preact 10, Vite 5 (`vite-plugin-singlefile`), `marked` for markdown, vitest + @testing-library/preact; extension: `@types/vscode` ^1.100, esbuild, vitest for unit tests, `@vscode/test-electron` for the smoke test, `@vscode/vsce` for packaging.

**Spec:** `docs/superpowers/specs/2026-10-20-localpilot-design.md` (§4.2, §4.4, §5.2, §7, §8.1, §8.3, §9). Protocol source of truth: `core/src/protocol.rs` (+ `docs/superpowers/notes/2026-10-21-core-bench.md` for expected timings). Executors read both.

## Global Constraints

- Wire protocol = `core/src/protocol.rs` exactly: camelCase JSON; method strings from `protocol::methods`; `Position.character` in UTF-16 code units (VS Code's native unit); `chat/send` returns `{}` immediately and `chat/done` ends the turn; `initialize` returns `indexStatus: "building"` and `index/ready` may arrive **before** the `initialize` response; notifications sent before the `initialize` response are dropped by the core — clients must await `initialize` first; "turn already running" is error `-32602`; core `-32603` = internal error.
- Core binary: bundled at `vscode/bin/<target-triple>/localpilot-core` (v1: `aarch64-apple-darwin`), overridable by setting `localpilot.coreBinaryPath`. Spawned as `localpilot-core serve --workspace <root> --log-level <level>`; one process per VS Code window; stdin close = shutdown; auto-restart at most 3 times per minute on crash, then show an error.
- Never auto-start Ollama. `status.ollama == "down"` → status-bar warning + one-click "Start Ollama" that opens a terminal running `ollama serve`, plus "Retry". `modelMissing` → offer `ollama/pull` with progress.
- Settings (all under `localpilot.*`, forwarded verbatim in `initialize.settings`): `ollamaUrl` (default `http://localhost:11434`), `completionModel` (`qwen2.5-coder:0.5b-base` — measured decision, see docs/superpowers/notes/2026-10-21-core-bench.md; `1.5b-base` is the quality alternative), `chatModel` (`qwen3.8:27b-mlx`), `completionsEnabled` (true), `completionDebounceMs` (120), `completionMaxTokens` (32), `chatThinking` (`off`|`on`), `coreBinaryPath` (""), `allowedCommandsAlways` ([]), `completionContextTokens` (3584), `chatContextTokens` (24000), `logLevel` (`info`). Changing any setting restarts the core (the core takes settings only at `initialize`).
- Completions: fire after `completionDebounceMs` of no typing; cancel the in-flight request (`completion/cancel`) on the next keystroke or when VS Code's `CancellationToken` fires; empty `items` → no suggestion; report `completion/accepted` / `completion/rejected`.
- Approved edits are applied with `WorkspaceEdit` **and saved** (`save: true`) only for the files touched; files not open are opened in the background, edited, saved; undo stack must cover the change.
- `run_command` runs via `child_process.spawn` with `shell: true`, cwd = workspace (or `cwd` param), output captured (stdout/stderr truncated to 16 KB each) **and** echoed to a "LocalPilot" output channel; 10-minute hard timeout.
- Webview: `localResourceRoots` limited to the extension; CSP `default-src 'none'; style-src 'unsafe-inline' ${cspSource}; script-src 'nonce-…'; img-src ${cspSource} data:`; no external network from the webview; `retainContextWhenHidden: true`.
- Chat UI must render in both VS Code light/dark/high-contrast themes using `--vscode-*` CSS variables (JetBrains later injects equivalents).
- Keybinding: `Cmd+Shift+L` (mac) / `Ctrl+Shift+L` opens the chat view; activity-bar icon "LocalPilot".
- No telemetry, no network calls other than the core's own.
- `npm test` green, `npm run lint` (eslint + tsc --noEmit) clean, before each commit; conventional commit messages.

## Review Focus

1. **Document sync vs. completions ordering** — a `didChange` must be sent before the `completion/request` for the same keystroke; the core applies notifications in order, so the client must never reorder them (Task 5 test).
2. **Multi-root / non-file documents** — untitled or non-`file:` scheme documents (settings, output panes, git diffs) must not be synced or completed; only the first workspace folder is the root (Task 5).
3. **Core crash mid-chat** — the process dying during a streaming turn must end the UI turn with an error state, not a spinner forever, and completions must keep working after restart (Task 4 + Task 7).
4. **Approval with edited args** — the user edits the command in the tool card before approving; the edited string must reach `chat/approve.editedArgs` and the "always" key must be the edited command (Task 3 + Task 7).
5. **Large diffs in the tool card** — a 2000-line diff preview must not freeze the webview (virtualize or collapse beyond N lines; Task 3).

### Task 5: Document sync + inline completions

**Files:** `vscode/src/{documentSync.ts,inlineProvider.ts}`, `vscode/test/{documentSync.test.ts,inlineProvider.test.ts}`

**Interfaces — Produces:**
- `DocumentSync(client, root)`: subscribes to `onDidOpenTextDocument/onDidChangeTextDocument/onDidCloseTextDocument/onDidSaveTextDocument`; sends `didOpen` for already-open docs on start/restart; only `file:` scheme under `root`; `didChange` uses `contentChanges` → `[{ range, text }]` (VS Code ranges are already UTF-16 `{line, character}`); versions forwarded; exported pure helper `toContentChanges(e)` and `isSyncable(doc, root)`.
- `InlineProvider(client, settings)`: `provideInlineCompletionItems(doc, pos, ctx, token)`: skip if `!completionsEnabled` or doc not syncable; debounce `completionDebounceMs` (resets on each call; previous in-flight request → `completion/cancel`); send `completion/request { uri, position, requestId }`; token cancellation → `completion/cancel`; map `items` to `InlineCompletionItem { insertText, range }`; `completion/accepted` via a `command` on the item (`localpilot.completionAccepted`), `completion/rejected` when a new request supersedes an unaccepted one. Exposes `Debouncer` class (pure, testable with fake timers).
- Ordering guarantee: `DocumentSync` sends `didChange` synchronously inside the VS Code change event, and `InlineProvider` is invoked by VS Code after the change event — add a test with a fake client that records the order (Review Focus 1).
- **Notebook cells (user requirement, 2026-10-21):** documents with scheme `vscode-notebook-cell` (cells of an `.ipynb` under the root) are syncable too. The core keys its overlay by file path, so each cell is sent as a virtual file: `didOpen` with URI `file://<notebook path>.cell<index>.<ext>` (ext from the cell language: `py`, `js`, …; markdown cells are not synced). Because the core only sees one cell per document, `DocumentSync` also maintains one synthetic sibling document per notebook, `file://<notebook path>.cells.<ext>`, holding all code cells concatenated in order (re-sent as a full-text `didChange` on any cell change, debounced 200 ms); the core's related-snippet retrieval picks it up as a recently-edited sibling, giving the model prior-cell context. `InlineProvider` completes inside code cells only. Exported helpers `notebookCellUri(cellDoc): string | undefined` and `isNotebookCell(doc)`; closing the notebook `didClose`s every virtual document. The e2e/manual checklist in Task 7 must include a notebook.
